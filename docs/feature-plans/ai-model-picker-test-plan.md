# AI model picker — test plan (tester pass)

Written before implementation, per `CLAUDE.md`'s Agent Workflow step 4. This is the acceptance
bar the senior-developer implements against; it contains no test code. Companion to
`docs/feature-plans/ai-model-picker.md` (architect's plan — schema, contracts, services, routes,
error path) and the ui-designer's component spec for `components/settings/ai-categorization-section.tsx`
handed in the same task. Mirrors `docs/feature-plans/byok-llm-assisted-categorization-test-plan.md`'s
structure (per-file tables, unit then e2e).

Prisma stays mocked via `vi.hoisted` + `vi.mock('@/lib/db/prisma', ...)`, per the existing suites.
Provider HTTP calls stay mocked at `global.fetch` (adapter tests) or at the `lib/ai/index.ts` client
boundary (service tests) — no real network call in any unit test.

## 3. Spec-level gaps and ambiguities found while writing this plan — flagged, not resolved

1. **`listAiModels`'s backfill race is unspecified.** §5c step 5 computes `selectedModelId = models[0].id` and fires the guarded `updateMany`, but never checks that `updateMany`'s `count`. If a concurrent tab already backfilled a _different_ value between the read and this write (both racing the same null-guard), this render still returns the value it computed locally, which may not match what's now in the DB. Low-stakes (next render reconciles), but not written down anywhere in the architect's doc. Test plan §1f pins down "not consulted" as the behavior to test against; flagging that this should be an explicit product/architecture decision, not something the tester silently inferred.
2. **ui-designer §3c (`outcome: 'unavailable'`, `selectedModelId: null`) was a gap the architect's doc left open** ("open question 5" only covers the _stored-id_ unavailable case) — the ui-designer resolved it by omission (notice only, no select) rather than inventing a new visual pattern. This plan treats that resolution as settled, not as still-open, per the ui-designer spec text — flagging it here only so the record is explicit that a real gap existed and where it was closed.
3. **"Key/provider change resets model selection" is untested by the architect's own doc for the _same-provider, new-key_ case**, only for a provider swap. The architecture doc's rationale ("the full-row upsert writes the column unconditionally") implies both cases behave identically, but no example walks through same-provider re-save. §2b's e2e case is written broadly enough to cover either interpretation; flag to the architect if same-provider re-save is meant to behave differently (e.g. preserving a hand-picked model across a same-provider key rotation) — nothing in the doc suggests that, but it's also never explicitly ruled out.
4. **§7's placement note ("above the `ServiceValidationError` branch") has no test-observable effect**, since `AiModelRejectedError` doesn't extend `ServiceValidationError`. Noted in §1d so the developer doesn't spend effort preserving a source-order property that isn't actually load-bearing; the mapping output is what matters and is what's tested.
5. **Known non-coverage: `savedModels` accidentally spread into `settings` state.** The ui-designer's spec calls out that `doSave`'s response destructuring must pull `models` out separately (`savedModels`) so it isn't wrongly spread into the `settings` object. Nothing in this plan can catch a regression there: this repo has no component-level unit tests (only `tests/unit/services/` and `tests/unit/lib/`), and a stray `models` key sitting unused on the `settings` object renders identically in e2e — the picker would still populate correctly from the (also-set) `modelState`. This is a code-review-time check, not a test-suite-time one; flagging it here so it isn't assumed covered.
